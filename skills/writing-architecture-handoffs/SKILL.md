# 写架构交接文档

## 目标

把“讨论过什么”压缩成“下一位 agent 继续推进所必需的决策上下文”。

优先交付清晰的约束、方案取舍、推荐方向和执行边界，不写成长篇纪要。

## 执行方式

### 1. 先收集决策信息

从现有文档、对话或设计稿中提取以下内容：

- 当前实现或现状
- 用户真正关心的目标
- 不可违反的约束
- 可接受的退化或 trade-off
- 讨论过的候选方案
- 为什么最终更倾向某个方向
- 下一位 agent 第一版应做什么、不应做什么

不要按时间顺序复述对话，改为按决策价值重组材料。

### 2. 先写约束，再写方案

先明确：

- 目标是什么
- 哪些能力不能丢
- 哪些能力可以退化
- 用户到底是在要“明显收益”还是“低风险改造”

再写方案比较和推荐方向。这样能避免下一位 agent 重新发散。

### 3. 把方案写成“取舍结论”

当存在多个候选方案时：

- 不要平铺介绍
- 必须写清每个方案的主要优点和主要代价
- 必须明确说明为什么不选另外的方案
- 必须输出最终推荐方向

如果某个技术点容易被误解，例如某组件只是 pruning 而不是主索引，单独抽一节定性它的职责边界。

### 4. 明确“保留什么，放弃什么”

专门写出：

- 必须保留的能力
- 可以接受的语义退化
- 为了收益而有意识放弃的旧能力

这部分要帮助下一位 agent 避免“修着修着又把原目标改回去”。

### 5. 给出务实的下一步

优先推荐第一版能落地的方案，而不是理论最完整的方案。

必须同时写清：

- 第一版先做什么
- 第一版不要做什么
- 哪些复杂优化应推迟到后续版本

## 输出约定

### 当用户要你写交接文档时

默认输出以下结构，除非用户明确要求更短或更长：

1. 背景
2. 用户目标与约束
3. 已讨论方案与取舍
4. 关键技术结论
5. 必须保留的能力 / 可接受退化
6. 推荐方向
7. 第一版实现边界
8. 给下一位 agent 的一句话交接

每一节只保留能影响后续实现决策的信息。

### 当用户要你总结某份 handoff 写得好的地方时

默认输出：

1. 这份 handoff 写得好的 3-5 点
2. 它隐含的结构模式
3. 哪些写法最值得复用
4. 如果继续复写，这份 handoff 还缺什么

重点评价“是否降低了后续 agent 的决策成本”，不要泛泛夸写作风格。

## 约束

- 不要写成会议纪要
- 不要把所有讨论细节原样搬运
- 不要只写最终结论而省略取舍原因
- 不要省略“不做什么”
- 不要给抽象建议，必须落到下一位 agent 可以直接接手的粒度

## 完成标准

完成时确认输出同时满足以下条件：

- 下一位 agent 不需要重读整段历史，也能理解问题边界
- 用户关心的约束被明确写出
- 推荐方向和放弃方向都讲清楚
- 第一版范围被收紧，没有过度设计
- 结尾有一句可以直接复用的任务定义

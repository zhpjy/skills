# 每日工作总结

将“与我相关”限定为两类会话：他人明确 @ 当前用户，或当前用户当天发言参与。目标是形成“我的事项”清单，而不是罗列所有出现过的工作话题。每个事项都要先判断当前用户是否是责任人，再判断最新状态。

## 1. 收集证据

1. 先加载 `dws` skill，并使用 `dws profile list --format json` 获取当前用户的 `userId`、姓名和当前账号。
2. 获取本地当前时间，计算当天 `00:00:00` 至当前时刻的 RFC3339 时间窗。
3. 用下列只读命令收集候选消息，保留 reaction 字段以识别 `DONE` 完成信号，所有 `dws` 命令均加 `--format json`：

```bash
dws chat +search-msg --at-me --start "<start>" --end "<end>" --page-all --page-limit 5 --limit 100 --format json
dws chat message list-by-sender --sender-user-id "<current-user-id>" --start "<start>" --end "<end>" --limit 100 --cursor 0 --format json
```

4. 先按会话和业务主题合并候选消息，再补读每个事项的闭环上下文。`list-by-sender` 只返回当前用户的消息，不能用来证明没有收到回复；凡是当前用户发出的问句、咨询、求助、短句、通知，或候选消息看不出责任人/结果时，必须用稳定 `openConversationId` 读取同一会话前后消息。以事项发生时间为边界，读取不超过 50 条消息；必要时分别读取 `older` 和 `newer` 两个方向。

```bash
dws chat +chat-messages --group "<openConversationId>" --time "<time>" --direction newer --page-all --page-limit 2 --max-results 50 --format json
```

5. 对补读结果检查消息时间、发送人和会话名称。若分页结果不完整、上下文缺失或无法确认对方是否答复，只能标为“待核验”，不能直接标为“待处理”。
6. 搜索结果只给单聊标题，群聊不返回会话名称。应用会话级排除规则或填写聊天对象前，对去重后的群聊 `conversationId` 逐个调用一次 `dws chat conversation-info --group "<openConversationId>" --format json` 获取真实 `title`，不要根据消息内容猜测群名。

**完成条件：** 每个保留事项都有闭环证据，能回答“谁提出、谁负责、当前用户做了什么、最后结果是什么”；不能回答责任归属的事项不进入个人待办表。

## 2. 提炼事项

按业务动作合并同一问题的提问、回复、告警和后续确认。优先保留有明确交付、异常、承诺、责任分配、阻塞或结果的消息。

- **先判责任，再判状态：** 内部为每个候选标记“当前用户责任 / 他人责任 / 纯信息”，不把责任字段展示为表格列。只有当前用户需要完成、跟进、确认、排查或交付，才属于个人事项。
- **他人 @ 当前用户：** 若内容是请求、指派、追问或截止要求，作为当前用户事项候选；若只是抄送、通知或值班信息，仍需确认是否有当前用户动作。
- **当前用户 @ 他人：** 若是“知悉、通知、同步、请大家了解”等信息发布，默认排除，不因其中存在“待调整”“未来会”等词而标为未完成；若明确把动作交给他人，也不算当前用户待办，除非上下文显示当前用户还有明确后续动作。
- **当前用户向他人咨询或求助：** 这是“等待答复”的临时事项候选，必须补读对方回复。对方给出答案、链接、方案、示例或明确解释后，标记为已完成/已解决；没有回复才可标为待核验或待跟进。
- **当前用户主动处理工作：** “已上传、已发送、已刷新、已修复、解决了、已经设置好了”等是已完成证据；“我还没做、稍后处理、需要我确认”等才是未完成证据。
- **对方的答复或交付：** 对方回复“可以了、已处理、已创建、已发布”，或提供可用链接/示例，优先作为闭环证据，不能因为当前用户没有再次回复就判定未完成。
- 收录：直接指派给当前用户、当前用户明确负责的告警、当前用户主动推进且仍有本人后续动作、与当前用户交付物相关的结果确认。
- 排除：纯旁观讨论、纯信息通知、他人负责且当前用户未介入的告警、已得到答复的普通咨询、无行动含义的表情或寒暄。
- 单聊中家人、生活、情感等纯私聊话题按会话直接排除；同一单聊里若还有明确业务问答或动作，只保留业务部分。
- 会话级排除规则（无需补读上下文，直接不进入事项表）：
  - 「数据组告警通知」群的任务运行超时告警：告警文案表明超时不超过 20 分钟的（如“任务运行时长超15分钟”）无需处理，直接排除；仅“超30分钟”等超过 20 分钟的告警按责任判定正常收录。
  - 「东南亚快递数据组」群中机器人（如 `Robot-D`、`小橘`）发送的互动卡片、Job 通知或执行结果消息，一律不作为当前用户事项，即使被 @ 也直接排除。
- 同一事项出现多次时，以当天最后的明确消息为准；后续消息可以将状态提升为完成，也可以重新打开事项。不要用“没有看到当前用户后续发言”推断未完成。
- 除 `DONE` 和 `我看看` 外，不从“已读”或普通表情回应推断完成；没有足够上下文时写“待核验”，不要擅自写成“待处理”。
- 用户提供上一日总结或要求续办时，保留其中未完成事项，标注“昨日续办”，并用今天的消息更新状态。
- 每个事项记录消息返回的会话名称：单聊写对方姓名，群聊写“群名称：发消息人1、发消息人2”；同一事项来自多个会话时用顿号合并，最多列出三个最相关会话。名称缺失时写“未命名会话”，不要根据消息内容猜测名称。

## 3. 输出日报表

默认只在对话中输出，不创建待办、不发送消息、不改写任何钉钉内容。使用中文、简洁的 Markdown 表格：

```markdown
## YYYY-MM-DD 工作事项总结（截至 HH:mm）

| 状态 | 事项 | 聊天对象 | 结果 / 当前状态 | 相关说明 |
|---|---|---|---|---|
| 🔴 | … | 对方姓名，或“群名称：发消息人1、发消息人2” | **待处理** | … |

**图例：** 🔴 待处理或阻塞　🟠 已定位/部分完成　🟡 跟进中或待核验　🟢 已确认完成
```

状态必须反映责任和证据，而不是紧迫感：

- `🔴`：当前用户仍需处理，或存在明确阻塞、异常、截止风险。
- `🟠`：已完成定位或部分修复，但依赖他人、重跑或后续动作。
- `🟡`：工作正在推进，或已通知但尚无可验证结果。
- `🟢`：聊天中已明确确认结果完成；必要时说明仍需例行核验。

状态判定补充：

- 信息通知本身不使用 `🟡`；若没有当前用户后续动作，直接排除。
- 咨询类事项在收到有效答复后使用 `🟢`，不要因为话题仍可能继续而保留为待办。
- 当前用户明确声明处理完成（如“刷好了”“改好了”），只是对方回复“我看下”仍在核验时，使用 `🟢` 并注明“待对方核验”，不因核验未完成而保留为待办。
- 消息的 `reactions.details[].emoji` 为 `DONE`（大小写不敏感）时，直接视为该事项已完成，使用 `🟢`；不要求另有文字确认。其他 emoji 不触发完成状态。
- 当前用户发出的文字“我看看”，或当前用户添加的 `reactions.details[].emoji` 为“我看看”时，视为当前用户正在处理，使用 `🟡` 并写明“正在处理”。同一事项后续出现 `DONE` 时，以 `DONE` 的 `🟢 已完成` 状态为准。
- 只看到单方面消息、上下文读取不完整或责任人不明时使用 `🟡 待核验`，不要使用 `🔴 待处理`。

在表格后用一句话说明筛选范围，例如“按被 @ 和本人参与的会话筛选，未纳入纯旁观及非本人负责的值班告警”。

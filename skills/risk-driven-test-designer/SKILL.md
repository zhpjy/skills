# 风险驱动测试设计

目标：提高测试的回归保护能力，同时控制数量、执行成本和维护成本。不要把“多写测试”当作目标。

## 工作方式

根据任务选择模式，可组合使用：

- **分析**：识别行为、风险、已有覆盖和测试缺口，不修改代码。
- **实现**：设计并创建最小充分测试集，运行验证。
- **审查**：检查已有测试的价值、稳定性、重复和实现耦合。
- **结构**：规划或检查测试目录；除非用户明确要求，不批量迁移历史测试。

## 默认流程

1. **理解上下文**
   - 先阅读需求、变更、缺陷描述、公开接口和关键领域代码。
   - 查找已有测试、测试框架、命名、fixture、Fake、CI 与测试发现规则。
   - 项目约定优先于本 Skill；只有缺少约定或约定明显失效时才提出调整。

2. **识别测试对象**
   - 从可观察行为、业务规则、状态变化、契约、不变量和失败模式出发。
   - 不要按类、方法、分支或代码行机械枚举测试。
   - 特别检查资金、权限、并发、幂等、时间、重试、恢复、数据一致性和外部依赖风险。

3. **决定是否需要测试**
   对每个重要候选项判断：
   - 它防止什么真实故障？
   - 失败影响和发生可能性如何？
   - 是否已有等价覆盖？
   - 测试能否稳定判定正确结果？
   - 回归保护是否值得执行与维护成本？

   无法说明真实风险或删除后不会明显降低信心的测试，默认不生成。

4. **选择最低充分层级**
   - 规则、计算、状态机、不变量：优先领域或单元层。
   - 数据库约束、事务、组件协作：优先组件或集成层。
   - HTTP、消息、文件和第三方格式：优先契约层。
   - 核心用户目标：保留少量端到端黄金路径和关键失败路径。
   - 真实外部环境可用性：使用探测脚本或人工场景，不混入默认回归测试。

   仅在风险很高或不同层验证不同性质时重复覆盖。

5. **设计最小充分测试集**
   通常优先选择：
   - 一个代表性成功场景；
   - 一个最重要失败场景；
   - 必要的边界、状态转换或不变量；
   - 缺陷修复对应的回归场景。

   输入组合较多时，优先参数化、表驱动、性质测试或状态机测试，不复制相似用例。

6. **实现与验证**
   - 沿用项目现有框架和风格，不另建平行测试体系。
   - 测试公开行为和可观察结果，不直接测试私有方法。
   - 优先真实对象或轻量 Fake；仅在明确边界使用 Stub 或 Mock。
   - 避免固定 sleep、真实当前时间、无种子随机数、执行顺序依赖、真实公网和共享可变状态。
   - 一个测试表达一个业务原因，可以包含共同证明该结果的多个断言。
   - 测试名称表达“条件/行为/结果”，不要只写方法名或 success。
   - 运行相关测试；不能运行时明确说明，不得声称已通过。
   - 对关键测试，尽可能确认目标行为被破坏时测试会失败；可使用轻量变异或静态反事实检查。

7. **汇报结果**
   根据任务裁剪输出，避免形式主义。通常说明：
   - 识别的关键行为与风险；
   - 新增、修改或建议的测试及其层级理由；
   - 重要的未生成项与剩余风险；
   - 实际执行结果。

## 不要机械生成的测试

通常不单独测试：

- 简单 getter、setter、常量、纯转发和框架生成代码；
- 私有方法和内部调用顺序；
- 不构成契约的日志完整文本；
- 静态配置值本身；
- 仅为提高行覆盖率而存在的分支；
- 已在更低层充分覆盖的相同条件组合。

但以下情况仍需考虑测试：

- 配置校验、危险默认值及配置对行为的影响；
- 日志或数据格式是机器接口、审计要求或安全边界；
- 简单代码承载高影响业务规则；
- 历史缺陷表明该行为容易回归。

## 未生成项与剩余风险

不要穷举所有没写的测试。只说明：

- 用户明确要求但未生成的项；
- 看似重要但已有替代覆盖的项；
- 被主动排除的典型低价值项；
- 因环境、数据或可测试性限制而未覆盖的高风险项。

每项尽量说明原因、替代覆盖和是否留下剩余风险。这用于证明测试范围经过选择，而不是要求冗长解释。

## 判断尺度

这些规则是决策原则，不是硬性配额。根据项目规模、风险、法规、团队能力和现有约定调整。遇到多个合理方案时，选择更简单、稳定、易定位且维护成本较低的方案，并简要说明取舍。

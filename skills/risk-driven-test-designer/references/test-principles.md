# 测试选择与质量原则

## 一、价值判断

可用以下维度做定性判断，不要虚构精确分数：

- 业务影响：低 / 中 / 高 / 关键
- 失败可能性：低 / 中 / 高
- 变化或历史缺陷概率：低 / 中 / 高
- 测试发现能力：弱 / 中 / 强
- 执行与维护成本：低 / 中 / 高

倾向：

- 高风险、低成本：优先测试。
- 高风险、高成本：寻找更低层或更可控的测试。
- 低风险、高成本：通常不测试。
- 低风险、低成本：只有能防止明确回归时才测试。

## 二、可靠判定依据

自动化测试至少应验证一种稳定的可观察结果：

- 返回值或错误类型；
- 状态变化；
- 持久化结果；
- 发出的事件；
- 外部可见副作用；
- 契约或 Schema；
- 前置条件、后置条件或不变量。

以下内容通常不能单独证明业务正确：

- 仅仅没有抛异常；
- 打印响应供人查看；
- 私有方法被调用；
- Mock 调用次数或内部调用顺序；
- 与业务无关的内部字段值。

## 三、Mock 与隔离

优先顺序可参考：真实对象 → 内存 Fake → Stub → Mock。

适合隔离：

- 真实第三方、网络、时间、随机数、文件系统；
- 慢速、不稳定或本地无法提供的基础设施；
- 清晰的端口、适配器和进程边界。

避免为了断言实现路径而 Mock 被测对象内部结构。Mock 不是越少越好，关键是不要让测试与实现细节绑定。

## 四、缺陷回归

处理缺陷修复时：

1. 提取缺陷的外部表现。
2. 找到稳定复现它的最低层级。
3. 尽可能先确认测试在修复前失败。
4. 确认修复后通过。
5. 检查附近具有相同根因的边界。
6. 不为无关代码补测试。

## 五、审查已有测试

重点识别：

- 没有明确风险或判定依据；
- 与其他层重复覆盖；
- 直接测试私有实现；
- 过度 Mock 或只断言调用关系；
- 固定等待、真实时间或外网依赖；
- 测试之间共享状态或依赖顺序；
- 一次验证多个无关业务原因；
- 重构不改变行为却导致大量测试失败；
- 生产逻辑被破坏后仍然通过。

处理方式可以是保留、合并、下沉、改写为参数化、改成人工/探测，或删除。删除前确认它没有承担隐含契约。
